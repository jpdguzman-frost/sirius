## Questions answered back, from the code rather than by asking

- **#69, the field key.** No divergence to record — it was already `requestor`
  end to end. `intake-parser.ts:54-55` maps both `requestor` and
  `primary requestor`; the API never returned `client`. The rename was
  display-only.
- **#70/#72/#73/#74, can the forecast come from ARES.** No, not per row.
  `computeDeliveryForecast()` (`ares/src/services/demandService.js:300`) is a
  Monte-Carlo simulation over daily throughput vs total demand cards — it
  answers "when does this queue of N finish" and converts with
  `addWorkingDays(today, days)`. Finest granularity is `perLane`. Its axis is
  **lane/discipline × throughput**, never difficulty. `computeCardCycleTime()`
  is per-card but backward-looking: measured dwell on cards that already
  moved. So the existing split is the right one — ARES supplies the
  measurements, Sirius derives the per-item date. The two quantities are not
  interchangeable.
- **#72/#74, does anything still consume review time.** Yes, and in a place
  nobody would look: `late` was `renderDelivery > deadline`, and
  `renderDelivery` counts from the Friday of the sketch-approval week. The
  client's wait was inside **every** past-deadline warning in the product.
  Defensible while the schedule drew a review segment and auto-placed render
  behind it; not defensible once #71 removed the bar and #72 made render a
  hand-placed row — review then drove a warning while being visible nowhere
  and adjustable nowhere, the one control that could move it having left with
  the Forecast tab. → ruling 3.

## Two review passes, then deploy

`/simplify` (4 agents, 17 findings, 16 applied) then `/code-review` (12
findings, 9 applied, 3 flagged). **Three real defects, all in the same day's
own work, none of which the suite could have caught as written.**

1. **Raw-string `workday()`.** `new Date('2026-08-03')` is UTC midnight, so
   west of UTC the working-day walk starts a day early — 08-04 against 08-05
   under America/New_York. Both new call sites did it; no pre-existing caller
   does, the engine included. Invisible to CI because the dual-TZ suite runs
   UTC and Manila, **both at or ahead of UTC**. The new guard flips TZ itself
   and was proved to fail against the old code.
2. **Rounding.** `workday()` rounds its argument, so walking two phases
   separately ≠ walking their sum once. `workFinishOf` summed. All three
   difficulties disagree; Medium and Hard ran a working day EARLY — the
   dangerous direction, a missed past-deadline warning. Now mirrors the
   engine's phase-by-phase walk.
3. **The design cell was chosen by the card's TITLE.** `laneOf` matches
   `/asset|illustrat|render|icon/` and every real task prefix matches it, so
   every task card classified `assets` — a 13.88-day cell for an Easy card
   instead of 0.94. Masked entirely because every fixture was Medium, which
   has no assets cell and silently falls back. Now classified on the card's
   list.

## The model: frozen, and phase 19 opened

JP: *"there's no model yet in place, this has to be built separately"* — and
after measuring production, that is the correct reading even though phase 6 is
marked signed off.

**What exists.** The pipeline is real and healthy: 19,860 `card_events` from
ARES movements, 1,942 samples, 24 grid cells written by a run that SUCCEEDED at
03:38 this morning. So the machinery JP described — a static grid from ARES
data, keyed on classification — is built.

**What it produces is unusable.**

| cell | learned p70 | n | reference |
|---|---|---|---|
| Easy/design | 0.32 d | 974 | 0.94 |
| Medium/design | **0.13 d** | 649 | 1.2 |
| Hard/design | 0.30 d | 56 | 2.09 |
| Easy/assets | 0.01 d | **1** | 13.88 |

Medium below Easy is not a plausible ordering and 0.13 days is about an hour.
Live provenance read `refreshed grid · 3 lanes from snapshot (sparse grid)` —
a **blend** of measured and reference figures, with the split moving nightly.

**Root cause.** `deriveSamples` measures dwell between CONSECUTIVE movement
events and drops open intervals — a card still sitting in a list has no next
event and contributes nothing. The cards that linger are the slow ones, so the
sample is structurally biased to fast cards.

**Frozen** (`3a86df0`): `model_frozen` on the project, **default true**, which
is invariant 7's release gate written down rather than implied. The freeze
gates the READ — the nightly refresh keeps running and keeps writing, because
those events are the raw material for the replacement. Verified live: both
projects now forecast `Medium/design` at the reference 1.2 d, with 20 and 4
measured cells held.

**Phase 19 opened** (T179–T183): store the tags ARES already sends us and we
throw away on work cards; read ARES's own `computeCardCycleTime` instead of
re-deriving; build the grid from completed cycles; add a sanity gate
(monotonicity, minimum n) before any cell may displace the snapshot; and settle
the two unruled questions (a work card's lane — own tags or MC group's; and
what percentile a sprint bar draws at).

**T179 is not housekeeping.** ARES sends `labels` on every card and the mapper
reads them, but only the deliverable keeps them. With no tags on a task card,
`loadSprintItems` had to infer lane from the TITLE — and every real prefix
matches `laneOf`'s asset regex. That is the same defect `/code-review` caught
this morning; classifying on the card's list is a workaround, the tags are the
fix. 686 of 686 live work cards already carry a difficulty label.
