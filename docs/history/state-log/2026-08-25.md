## What ARES still owes us — the concrete question

JP asked what is actually needed from ARES. It is one question with one
consequence.

**The mechanism.** When Sirius writes a registry field to Trello (urgency, due
date, difficulty) it stamps `registry_written_at` on the row. When the worker
re-reads that card through ARES it stamps `readAt` **at the instant it issues the
read**, and `staleGuard` in `worker/syncAres.ts` applies the Trello-owned fields
only where `registry_written_at < readAt`:

```js
$or: [{ registry_written_at: { $exists: false } },
      { registry_written_at: { $lt: readAt } }]
```

Read plainly: *if my write happened before I started this read, the payload
already reflects it — trust it. If my write happened after, the payload predates
the user's change — leave it alone.*

**The assumption underneath.** That the moment Sirius *issues* the read is a fair
proxy for the moment the data was *fetched from Trello*. That holds only if ARES
reads live.

**The failure if it doesn't.** If ARES serves from a cache, a payload can be
minutes old while the request is one second old. `readAt` would then be newer
than `registry_written_at`, the guard would pass, and the stale cached value
would be written over a change the user just made — the push reverting an edit,
which is the precise bug the guard exists to prevent. Invariant 8 promises
Sirius never shows a state Trello lacks; this is the one path where it could.

**The question for whoever owns ARES**: *does the read path serve cached data,
and if so what is its maximum age?*

- **Reads live** → the guard is exactly right, and the assumption is retired.
- **Cached, bounded by N** → `readAt` must become "issue time minus N".
- **Best answer** → ARES returns a `fetchedAt` / `asOf` per card, and Sirius
  compares against the age of the *data* rather than the age of the *request*.
  That is drift-proof, where a hardcoded N is not.

Product's position (owl #54) is that neither they nor Miles can see the ARES read
path and will not guess; it is with whoever owns ARES. Their instruction was to
leave it visible as an unverified assumption rather than quietly assume it
closed, which is how it is recorded in the source comment and here.

**Urgency: low but not zero.** It only bites when a user edits one of three
fields and a push for that same card lands inside the cache window. Nothing is
blocked on the answer; the guard is sound in principle and tested
(`test/reconcile.test.ts`). What is missing is confirmation of the one fact it
stands on.

## The ARES question is answered — from their source, not from an owl

JP asked whether I have access to the local file-drop owl for ARES. I do:
`../owl/` holds four notes, all outbound (`sirius-to-ares` #06–#09). Inbound
notes are deleted once processed, so an empty inbound side means either nothing
came or everything came and was handled — and here it means nothing came. The
channel was **closed 2026-08-19** on JP's instruction after three notes on one
one-line ask drew no reply: *"if nobody is reading `../owl/`, that is more worth
knowing than the subscription is."* Nobody was.

**But `../ares/` is a sibling directory of this repo.** The question we have been
waiting on since 2026-08-20 was answerable by reading it, and it took minutes.

### The answer

**ARES reads never touch Trello.**

```js
// ../ares/src/services/trelloDataService.js
export async function getCard(cardId) {
  return TrelloCard.findOne({ cardId }).lean();
}
```

The board endpoint is the same shape (`TrelloCard.find(filter)`). ARES serves a
**materialised store** that its own worker refreshes on a **15-minute cycle**
(`TRELLO_REFRESH_INTERVAL_MS = 15 * 60 * 1000`). Confirmed against the live API:
`/api/v1/trello/health` returned `lastRefreshAt` and `nextRefreshAt` exactly
fifteen minutes apart.

So a payload can be up to ~15 minutes old **no matter how recently you asked**.
The age of the response says nothing about the age of the data.

### The field that fixes it already exists

```js
// ../ares/src/workers/trelloCardLogic.js — buildCardDoc
lastPolledAt: now,
```

Written for **every non-done card on every cycle**, changed or not — so it is a
genuine *fetch* time, not a last-modified. It is in the schema, no projection
strips it, and a live card came back carrying it with an age that tracked the
cycle position exactly.

Field names on a live card:
`__v, _id, boardId, cardId, checklists, createdAt, currentList, currentListId,
dateLastActivity, description, due, dueComplete, firstSeenAt, historyFetched,
labels, laneHistory, lastPolledAt, members, movements, name, projectName,
status, updatedAt, url`

### The bug this exposes

`staleGuard` in `worker/syncAres.ts` applies Trello-owned fields only where
`registry_written_at < readAt`, and `readAt` is stamped **when Sirius issues the
request**. That is a fair proxy for when the data was fetched *only if ARES reads
live*. It does not.

The reachable sequence:

1. ARES polls card X at 10:00.
2. A user changes urgency in Sirius at 10:05; we write Trello and stamp
   `registry_written_at = 10:05`.
3. Anything triggers a reconcile of X at 10:06 — a push for the board, or the
   Sirius sync cycle.
4. `readAt = 10:06`, which is **later** than 10:05, so the guard passes.
5. We apply the payload ARES polled at **10:00** — before the edit — and the
   user's change is silently reverted.

The guard was built to prevent exactly this and cannot, because it compares
against the wrong clock.

### Why nothing is on fire

`writes_enabled` is **off** on rt-837 (JP, 2026-08-21). With no registry writes,
`registry_written_at` is never set, absent always passes the guard, and the whole
branch is inert. **The bug is latent, and it becomes live the moment writes are
switched on** — which makes it a gate item on that decision rather than a
standalone fix.

### The fix

Compare against `card.lastPolledAt` instead of the request instant. Same guard,
right clock:

- write at 10:05, data polled 10:00 → `10:05 > 10:00` → **skip**, correctly.
- write at 10:05, data polled 10:10 → `10:05 < 10:10` → apply, correctly.

It needs `lastPolledAt` carried through `AresCard` and the mapper into the two
upserts. It is small, and it is currently inert, so it can land before the
write-enable rather than alongside it.

**One dependency worth naming**: ARES's own 2026-08-02 integrity survey records
`lastPolledAt` as *"written in three places and read by none"*. If Sirius starts
depending on it, ARES must be told, or a future cleanup deletes the field and
takes the guard with it.

### A note on the record

`contracts/ares-read.md` already said *"everything documented is served from ARES
cache"* — and then the same bullet said *"per JP (2026-08-03) the new ARES
delivers in realtime"*. Two claims, opposite meanings, one line apart, both
second-hand. That is how the question stayed open for three weeks while the
answer sat in a sibling directory. The bullet is now replaced with what was
measured.

## Correction, same day — JP asked about the webhook, and he was right to

*"There's a polling from Ares but there's also a webhook that enables changes
from Trello to Ares. Did you validate that?"*

**No, I had not.** I saw webhook references in `trelloOrchestrator.js` while
tracing the read path, did not follow them, and reported "up to ~15 minutes old"
as the freshness bound from the poll interval alone. That bound is wrong as a
general statement.

### What the webhook actually does

`trelloWebhookWorker.processCard` **fetches the card live from Trello** on the
event —

```js
card = await trelloApi.getCard(cardId);
```

— and writes it through **`buildCardDoc`, the same function the poll uses**,
which stamps `lastPolledAt: now`.

### Measured, not inferred

Board `hLL7WW2V`, 200 cards, grouped by `lastPolledAt`:

```
2026-08-25T02:58:22.630Z -> 199 cards      the poll cycle
2026-08-25T03:03:04.820Z ->   1 card       five minutes off-cycle
```

One card, alone, five minutes after the cycle and ten before the next. That is a
single-card webhook refresh, live, on our own board. Trello → ARES webhooks are
running.

### What changes, and what does not

**Changes — the freshness claim.** A card that actually changed is refreshed
within seconds, not up to fifteen minutes. The poll is the floor for cards
nothing happened to, not the norm for cards that did.

**Does not change — the bug.** `staleGuard` still compares our write against the
instant we *issued* the request, which is not when the data was fetched no matter
which writer filled it. The window is smaller than I said, not absent: Sirius
writes at T, Trello fires, ARES re-fetches at ~T+2s — a reconcile at T+1s still
reads the pre-write copy and, under the current guard, reverts the edit.

**Strengthened — the fix.** This is the part JP's question improved. Had
`lastPolledAt` been poll-only, comparing against it would have been *over*-
conservative on webhook-refreshed cards: their data would be current while the
stamp looked stale, and we would skip reconciles we should apply. Both writers
share `buildCardDoc`, so the stamp tracks whichever path last fetched the card.
The fix is correct under polling, under webhooks, and under any future cadence —
which is precisely why comparing against a *measured fetch time* beats assuming a
number, and why the 15-minute figure should never have been load-bearing.

### Two places the stamp deliberately freezes

Found while checking this, and worth carrying into the fix:

- **Done cards.** The poll skips re-upserting a captured-done card
  (`isCapturedDoneCard`); live health reports `doneSkipped: 279` and `2674` on
  two boards. A done card's stamp only advances if a webhook fires for it.
- **`markArchived`** writes only `archived` / `archivedAt`.

Both fail in the **safe** direction for a staleness guard — the data looks older
than it is, so the guard skips rather than over-writes, which is the asymmetry
the code already argues for (a skipped reconcile costs a cycle and heals; an
applied stale one shows someone a value they did not choose). But a done card
edited manually in Trello on a board without webhooks could stop reconciling, so
the fix must decide that case deliberately rather than inherit it.

### One distinction to keep straight

**Trello → ARES webhook** and **ARES → Sirius push** are different channels.
`hLL7WW2V` demonstrably has the first — measured above — and demonstrably lacks
the second: zero push events across the entire 7-day TTL, which is what owl #09
reported before the channel was closed. ARES learns about that board's changes
within seconds and does not pass them on; we find out on our own reconcile. My
earlier note conflated nothing, but the two are easy to swap and the conclusions
are opposite.

## Built: the guard moves onto the fetch clock

JP approved the outline. Built as outlined, with one thing that went differently
and one of my own guards catching me.

### The shape, not the instance

The old signature took a `readAt: Date` and its doc comment warned:

> *required, never defaulted: a caller that passed `new Date()` here would
> disable the guard silently, which is the exact bug it exists to prevent.*

Both callers passed exactly that, because a read instant was the only clock they
had. **The warning was correct and it did not help.** So the parameter is gone
rather than corrected: the upserts read the fetch instant off the payload they
are already handed. There is no argument left to get wrong.

That also dissolved a problem the full sync used to reason about. It stamped one
clock before the board read and applied it to every card in the response —
"the widest stale window in the app", the comment said, one timestamp covering
hundreds of cards upserted over minutes. Each card now carries its own fetch
instant, so the widest-window question no longer exists to be answered.

### Absence is a value, not a default

`fetchedAtOf()` returns `null` when ARES sends no usable stamp, and the callers
must handle it. The tempting fallback — use the read instant — *is* the bug,
reinstated silently, and a fallback is exactly what a future edit reaches for.
So absence behaves as infinite staleness: keep our value, skip the registry
reconcile.

Skipping is safe but it must not be quiet. `SyncStats` gained `unstamped`,
counted per run into `sync_runs` (`stats` is `Mixed`, so no migration), plus a
warning naming the contract. Expected to be zero forever; non-zero means urgency,
due dates and difficulty have stopped reconciling.

The loud half is `scripts/ares-probe.mjs`, which now fetches a live card from the
busiest board and fails the build if `lastPolledAt` is missing. Endpoint-level
stability could never catch this: the path stays `stable` while the field leaves
the body. **Run live against production ARES — it passes.**

### The tests

`test/reconcile.test.ts` moved onto the fetch clock and gained the case that
names the defect:

```
10:00  ARES fetches the card
10:05  the user edits urgency; we write Trello and stamp
10:06  a reconcile fires and asks ARES for the card
```

Judged on the request instant the guard passed — `10:05 < 10:06` — and wrote the
10:00 payload over the edit. The test asserts the request instant is *later* than
the write, so it can only pass on the fetch clock.

**Proved non-vacuous.** Stubbing `fetchedAtOf` back to `new Date()` — the old
behaviour — fails six of the guard tests, including that one. Restored, all pass.
A second guard asserts the *shape*: neither upsert takes a `Date`, the guard body
contains no `new Date()`, and neither worker mints a `readAt`. Reintroducing the
parameter fails it, verified by doing so.

### Two fixtures were lying

`test/drain.test.ts` and `test/syncAres.test.ts` failed once the guard tightened,
because their ARES cards carried no `lastPolledAt` — so they were exercising the
skip path while asserting reconciliation. **The fixtures were wrong, not the
guard**; every real ARES card carries the field. Fixed the fixtures. Worth
recording because the tempting move when two unrelated suites go red is to soften
what you just tightened.

### My own guard caught me

The shape assertion sliced from `const staleGuard` to the next declaration —
which swept in `fetchedAtOf`'s doc comment, where the prose quotes `new Date()`
while explaining why it must never be the fallback. `test/CLAUDE.md` rule 3
already records this exact trap twice ("source-regex guards read RAW text —
comments included"), and both previous times the resolution was that the guard
was right and the scope was wrong. Same again: sliced to function bodies, not to
the next declaration.

## /simplify + /code-review over the day's work

Ran both over `d0f30fc..HEAD` at JP's request. Four cleanup agents, then an
adversarial review. **27 findings between them; 24 applied.**

### The one that mattered

`/code-review` found a **real bug I had introduced hours earlier**, in the fix
itself.

The guard's rule is "don't overwrite a registry field with a payload older than
our own write." I implemented "no fetch instant → skip the registry write
entirely." On a card Sirius has **never written** there is provably nothing to
protect — and the original design said so, with a `registry_written_at: {$exists:
false}` branch written for exactly that case. My early return made that branch
unreachable.

Consequence: with `lastPolledAt` absent, a brand-new Urgent card is created by
the unconditional upsert and then never receives its registry fields, so it lands
on the schema default — `urgency: 'Non-Urgent'`, no difficulty, no deadline.
**The guard would have manufactured the precise failure it exists to prevent: a
value the user did not choose.**

Unknown freshness now *narrows* the guard to never-written cards rather than
disabling the write. Regression test added and proved to fail against the
skip-entirely version.

Worth naming the pattern: the same instinct that made the fix good — "absence is
a value the caller must handle, never a default" — is what made this wrong. I
applied it one level too far out, at the whole write instead of at the
comparison.

### What the review got right that I had argued the other way

I had recorded the done-card stamp freeze as "fails safe, not a regression." The
review pushed back: safe for one cycle, but **permanent**, since ARES skips
captured-done cards entirely (`isCapturedDoneCard` → `continue`, no write —
verified in their source, and live health reports `doneSkipped` of 279 and 2,674).

Checking properly: the conclusion holds but my reasoning was too thin to support
it. It is acceptable **only because ARES's own copy is frozen too** — the poll is
not re-reading that card either, so no fresher truth is being withheld, and the
unblock is real (a Trello change fires the webhook, which advances the stamp
through the same `buildCardDoc`). The contract note said none of that. It does
now, including a "do not fix this with an expiry" — an expiry would re-admit the
stale payload the guard exists to reject.
