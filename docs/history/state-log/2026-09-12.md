## The fourth flake, diagnosed — it is a 5-SECOND BUDGET, not a mystery

Re-run on JP's word with the context rebuilt first: map generator `--check` clean, vite and
vitest caches cleared, bundle rebuilt. Cold-cache `TZ=UTC` went red (2 files, 3 tests), the
re-run green; `TZ=Asia/Manila` went red (1 file, 2 tests), the re-run green; the
date-sensitive set under `America/New_York` green throughout. Same suite every time:
`test/migrations-archive-acks.test.ts`.

This run finally captured the error text instead of just the counts:

```
Error: Test timed out in 5000ms.
MongoServerError: Source collection migration-011.conflict_acknowledgements does not exist
```

**The cause.** `vitest.config.ts` sets no `testTimeout`, so every `it` runs on vitest's
**5-second default**. That file is the only suite in the repo that spins up its OWN
`MongoMemoryServer` — deliberately, because `startTestDb()` runs the migrations on connect
and the interesting case is a database that already holds acknowledgements when the runner
reaches 011. Its `beforeAll` was given 120s; **its `it`s were not given anything.** Each one
runs all twelve migrations against a real in-memory mongod and drops the database in
`afterEach`, on a five-second budget, while eighty-three other files run in parallel.

Under that load the budget is exceeded, the test aborts MID-FLIGHT, and the half-finished
state produces the second, much scarier-looking error on a later test in the same file: 011
checks `listCollections` for the source, finds it, and by the time `rename` runs an aborted
neighbour's `dropDatabase` has taken it away. Hence a DIFFERENT test failing each run.

That accounts for every observation: only this file, rotating tests, green in isolation
(12/12), green on the re-run, and no whole-run duration tell — the run is ~40s because it is
the PER-TEST budget being blown, not the suite's total.

**The migration itself is not at fault and there is no deploy risk.** 011's guard is correct
(`listCollections` → return if absent → return if the archive already exists → rename, never
drop). Its check-then-rename window can only be exploited by a second concurrent runner, and
`grep` over `src`, `worker`, `server.js` shows `runMigrations` is called from **scripts
only** — never on boot — so web and worker cannot race it.

**Fix APPLIED on JP's yes, 2026-09-12.** `DB_MS = 60_000` on both `describe`s (Vitest takes
an options object as the second argument) and on `afterEach`/`afterAll`, with the reasoning
in the file so nobody raises it again without reading why.

**Proven, not assumed** — the same discipline as a guard proof. A probe case sleeping 6.5s
was inserted into the suite: **with** the option it passes; with the option removed from 011
alone it fails at `5006ms` with *"Test timed out in 5000ms."* So the option is genuinely
applied rather than silently ignored, which is the failure mode worth ruling out — a
mis-typed option would leave the budget at five seconds and the suite would look fixed.
Probe removed, file restored from the /tmp copy, suite 12/12.

The measurement that makes this unarguable: **the suite needs ~5.1s of test time running
completely alone**, against a 5s budget. It was never going to survive eighty-three files of
competition; it was failing on arithmetic, not on luck.

This is a realistic budget, not a retry and not a mask: a case that genuinely hangs still
fails, a minute later. If these ever approach a minute, that is a signal to investigate, not
to raise the number.
