**Audience**: the agent building this feature inside the **ARES codebase**. This document is

**Owner**: JP (jpdguzman@frostdesigngroup.com). Questions and undecided items go to JP.

## 1. Background & goal

ARES ingests Trello changes in realtime via Trello webhooks and serves that data through its
read API (`/api/v1/trello/*`). Downstream tools currently **poll** that API to notice changes.

This feature adds **outbound push**: when Trello data changes on a subscribed board, ARES
sends a signed webhook notification to registered subscriber URLs. The first subscriber is
**Sirius**, Frost's delivery-planning platform, which runs beside ARES on the same host.

**The core design rule — notification, then read.** A push event is a *trigger*, never a data
carrier. It says "card X on board Y changed"; the subscriber then re-reads the card from the
existing ARES read API. Consequences that simplify this build:

- The payload carries no card data — no field diffing, no payload versioning, no schema drift.
- Delivery may be **at-least-once and unordered**. Duplicates and stale events are harmless to
  the consumer by design. Never build exactly-once machinery.

## 2. Requirements

### APS-1 — Subscriber configuration

A subscriber registry, config- or env-driven (a config collection is acceptable if that is the
ARES convention). Each subscriber: `{ name, url, secret, boardIds[], enabled }`.
A single env-var-configured subscriber is an acceptable v1:

```
PUSH_SUBSCRIBER_NAME=sirius
PUSH_SUBSCRIBER_URL=http://127.0.0.1:3955/sirius/api/webhooks/ares   # loopback, same box; note the /sirius base path
PUSH_SUBSCRIBER_SECRET=<hex, provisioned by JP — same value configured on the subscriber>
PUSH_SUBSCRIBER_BOARDS=hLL7WW2V,tx8gDsTH        # comma-separated Trello board shortLinks/ids
```

Secrets live in server-side env only — never in the repo, a client bundle, logs, or error
messages.

### APS-2 — Trigger points

After ARES finishes processing an inbound Trello change (webhook or its own sync) affecting a
card on a subscribed board, enqueue an outbound event. Covered changes: card created, card
updated (any field), card moved between lists, label added/removed, due date changed, card
archived/unarchived. One event type covers all mutations of an existing card (see APS-3) —
do not build a per-field taxonomy.

### APS-3 — Envelope

`POST` JSON to the subscriber URL:

```json
{
  "delivery_id": "01J...",
  "sent_at": "2026-08-04T09:15:00Z",
  "events": [
    { "event_id": "01J...", "type": "card.changed", "board_id": "hLL7WW2V",
      "card_id": "abc123", "occurred_at": "2026-08-04T09:14:58Z" }
  ]
}
```

- `delivery_id`, `event_id`: ULIDs (or another monotonic unique id), generated by ARES.
  `event_id` is stable per event — a retried delivery re-sends the **same** `event_id`s.
- `type` is exactly one of:
  - `card.changed` — any mutation of an existing card (`card_id` required)
  - `card.created` — new card (`card_id` required)
  - `board.resync` — ARES asks the subscriber to fully re-read the board (`card_id` absent).
    Emit after ARES recovers from its own outage or rebuilds a board, and on demand.
- `events` may batch (see APS-6). `occurred_at` / `sent_at` are ISO-8601 UTC.

### APS-4 — Delivery & signing

Headers on every delivery:

```
Content-Type: application/json
X-Ares-Delivery: <delivery_id>
X-Ares-Timestamp: <ISO-8601 UTC, time of this send attempt>
X-Ares-Signature: sha256=<hex>
```

- Signature = `HMAC-SHA256(secret, "<X-Ares-Timestamp value>" + "." + "<raw request body>")`,
  hex-encoded. The timestamp is regenerated (and the signature recomputed) on each retry.
- HTTPS only. Request timeout 10 s. Any **2xx** = delivered; anything else (or timeout) = failed
  attempt.
- Expected subscriber responses: `202` accepted (body `{accepted, duplicates, ignored}`),
  `401` bad signature/timestamp. Treat `401` as a failed attempt (likely secret mismatch —
  surface it loudly in APS-8, it will not fix itself).

### APS-5 — Retry & dead-letter

- At-least-once with backoff: retry at ~1 m, 5 m, 30 m, 2 h, 6 h after the first failure
  (5 attempts total), then **dead-letter**: persist the delivery with its final error, keep at
  least 14 days, surface the count (APS-8). Exact schedule may follow ARES conventions; the
  shape (minutes → hours, bounded attempts, dead-letter) is required.
- Retries must not block or reorder new deliveries to the same subscriber.

### APS-6 — Coalescing

Debounce per card: multiple changes to the same card within a short window (10–30 s) may
collapse into one `card.changed` event. Batch pending events per subscriber into one delivery
(cap ~100 events; overflow rolls into the next delivery). Never delay an event more than the
debounce window plus send time.

### APS-7 — Isolation

Outbound push is **fully asynchronous** — a queue/worker per ARES's existing background-job
pattern. A slow or dead subscriber must never slow, block, or fail ARES ingestion, its read
API, or deliveries to other subscribers.

### APS-8 — Observability

- A delivery log (last N per subscriber): timestamp, delivery_id, event count, outcome,
  attempt number, response code.
- Counters visible to operators (health endpoint field or admin surface, per ARES convention):
  delivered / retrying / dead-lettered per subscriber.
- Never log the secret or a full signature; the ULIDs and outcomes are enough to debug.

### APS-9 — Non-goals

- No card data in payloads beyond the envelope above. No per-field event types.
- No exactly-once delivery, no ordering guarantees, no consumer-specific logic.
- No inbound/write API of any kind — this feature only emits.

## 3. Acceptance criteria

| # | Criterion |
|---|---|
| A1 | A card change on a subscribed board produces a delivery to the subscriber URL within 60 s (debounce included), signed per APS-4, and a mock subscriber verifies the signature independently |
| A2 | A change on a **non**-subscribed board produces no delivery |
| A3 | Subscriber down: retries follow APS-5 and the delivery dead-letters after the final attempt; ARES ingestion and read API remain unaffected throughout (APS-7) |
| A4 | A retried delivery carries the same `event_id`s with a fresh timestamp + signature |
| A5 | 20 rapid changes to one card within the debounce window arrive as ≤ 2 `card.changed` events for that card (APS-6) |
| A6 | `board.resync` can be triggered operationally and arrives with no `card_id` |
| A7 | Secret absent from all logs and error output; delivery log + counters visible (APS-8) |
| A8 | Unit tests: signature construction, retry schedule, coalescing. Integration test: end-to-end against a local mock subscriber asserting envelope, headers, and retry behavior |

## 4. First-subscriber facts (for integration testing)

The Sirius receiver at `POST /sirius/api/webhooks/ares` (BASE_PATH mount — the bare path 404s): verifies the APS-4 signature with a ±5 min
timestamp window, dedupes on `event_id`, and answers `202 {accepted, duplicates, ignored}` in
under 1 s — it defers all processing. It is safe to re-send generously: duplicates are counted
and dropped. Staging first: point the subscriber config at Sirius staging with the TEST board
(`tx8gDsTH`) before any production board is subscribed.
