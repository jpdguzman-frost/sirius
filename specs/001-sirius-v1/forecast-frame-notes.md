# Forecast frame notes — build-spec v1.2 §7.2/§7.3, nodes `279:22602` / `279:16649`

Layer-2 law for the Forecast tab, the last of the six tabs still running on its
pre-redesign markup. Unlike every other tab in this project **there is no owl
and there are no Figma annotations** — the frames carry none, the Rex note store
is empty, and a name search for `annotation` returns nothing. The written
requirement is `docs/product/build-spec-v1.2.md` §7.2/§7.3 and §8; the drawn
requirement is the two frames. Where they differ, each difference is ruled
below and none is silent.

Frames read:

| node | size | what it is |
|---|---|---|
| `279:22602` | 2832 × 1146 | **authoritative** — the whole two-tier table, all 24 columns visible |
| `279:16649` | 1440 × 1175 | the same table at the real viewport, scrolled to the far right |
| `279:15122` | 1440 × 1024 | earlier version, comparison only — it alone carries the *How this forecast works* drawer |

Asserted by `test/forecast-frame.test.ts` unless the last column says otherwise.

## The column model

| # | Rule | Asserted |
|---|---|---|
| **R-fc-a** | **24 drawn leaf columns under 7 group cells — 25 under 8 as built, `n` being the one addition (R-fc-s) — and the spans are DERIVED, never typed.** `FC_COLS` is the one column table; `forecastGroups` folds it into the tier-one row by `col.group`. Both header tiers and every body row render from that one list, in that one order, so a column cannot be added to the body without appearing in the header — the shear §7.2 warns about ("a mismatch shears the header from the rows") is impossible by construction rather than caught by a number. Frame spans 7+2+4+1+4+4+2 = 24, and both tiers sum to 2704px against the body's identical 24 widths. | Yes — the spans summed out of the rendered header and compared to the leaf count, both derived from the same render |
| **R-fc-b** | **The frame draws SEVEN leading columns where §7.2 lists six.** The spec's single `Request` is drawn as `MC #` + `DELIVERABLE`; that is the whole difference and the frame wins, because splitting the identifier off the name is what every other rebuilt table in this app already does. | Yes — the leading seven asserted by class, in order |
| **R-fc-c** | ⚠️ **TIER-ONE CELL 1 IS A BLANK SPACER, NOT A LABEL.** Its text node still holds the characters `MC #` but is set `visible: false`, so 888px of grey renders with no glyphs (pixel-verified). Built as an empty 7-column spacer. Do not resurrect the string — a group label over the identity columns would claim they are a group, and they are not. | Yes — the first tier-one cell asserted to carry no text and to span the leading columns |

## Three places the frame states something the shipped system contradicts

Each of these reverses drawn content. Each is one line to put back.

| # | Rule | Asserted |
|---|---|---|
| **R-fc-d** | 🚨 **THE MODEL CONSTANTS PANEL IN THE FRAME QUOTES THE RETIRED SPREADSHEET FORMULA.** The footer banner reads *Total Cycle Time · 1.28 × Forecasted Review Time + 2.96*. Those two numbers are `LEGACY_CYCLE` in `lib/model.ts` — the workbook regression that `lib/forecast.legacy.ts` implements, that `test/forecast.legacy.test.ts` asserts **against `legacyForecast` only**, and that **invariant 6 forbids UI code from ever showing** ("for migration tests only… never imported by UI code"). **SC-3 says it in the spec's own words: the spreadsheet formula "is never exposed" (BR-2, BR-3).** It is also not a description of the shipped engine, which computes `lead + design + review` twice over. Shipping the panel verbatim would have printed the exact constants the constitution retired, on the one screen whose whole purpose is that the retired model is gone. **The panel renders the SHIPPED engine's constants instead**, and the Total Cycle Time entry states the real relation including the fact that a Review SLA override makes the total differ from the two cycle columns. The other three constants the frame gives (render starts the Friday of the sketch-approval week · WORKDAY with PH holidays excluded · W is WEEKNUM of the start date) are all correct and are quoted as drawn. | Yes — the legacy coefficients asserted ABSENT from template, scripts and stylesheet, and the four constant keys asserted against the engine |
| **R-fc-e** | ⚠️ **THE SECOND BREAKDOWN GROUP IS LABELLED `SKETCH` IN THE FRAME. It ships as `RENDER`.** Tier-one cells 5 and 6 both read exactly `SKETCH`, confirmed three ways (Rex `characters`, `get_design_context`, and the pixel render), in both target frames. Three independent sources say the second block is the render breakdown: §7.2's own list, the fields it renders (`renderLead`/`renderDesign`/`renderReview`/`renderCycle`), and the frame's own sample figures, which differ between the two blocks. **A header that says SKETCH over render figures is a user-visible error, not a design choice** — and the same frame proves it carries typos, because it spells `CYLCE` in three headers while its own footer spells *Total Cycle Time* correctly. Raised to product rather than changed under them. | Yes — both group labels asserted, and the render block asserted to read its own four fields and never the sketch ones |
| **R-fc-f** | ⚠️ **`CYLCE` → `CYCLE`, three headers.** Same evidence as R-fc-e: the footer banner in the same frame spells it correctly. Shipped correct. | Yes — the misspelling asserted absent |
| **R-fc-g** | ⚠️ **The percentile select is headed `TYPE` in the frame. It ships as `CONFIDENCE`.** Its values are `Average / 70th pct / 85th pct / 95th pct`, the wire field is `confidence`, §7.2 names it Confidence — and **`TYPE` already means asset type in the Pipeline table**, so the drawn label would collide with an established column meaning one tab away. Raised to product. | Yes |
| **R-fc-h** | ⚠️ **§7.2 says "Difficulty read-only"; the frame draws it with a chevron.** Shipped **read-only** — a badge, no chevron, no menu. The difficulty write exists (registry W3, `setDifficulty()`) and is shipped on Pipeline, so this is not a capability question; it is whether a second write surface for a Trello-owned field opens on a tab whose own explanatory copy has always said *"Difficulty comes from the Trello card label and can't be edited here"*. That is product's call, not a styling one. Raised. | Yes — asserted that this view opens no difficulty menu and carries no write handler |

## What the frame settles that §7.2 got wrong

| # | Rule | Asserted |
|---|---|---|
| **R-fc-i** | **NO VERTICAL RULES ANYWHERE.** §7.2 asks for a 1px `--border-border` right rule at every group boundary. The frame draws none — scanlines across the body are pure white from edge to edge — and **no shipped table in this app has ever had a vertical rule** (`25-requests.css`: *"no vertical rules — JP 2026-08-14"*). Group boundaries are carried by the header tier alone. Following §7.2 here would have introduced the first vertical rule in the product, against both the frame and the house. | Yes — asserted that no new rule declares a vertical border |
| **R-fc-j** | **The ONE rule the frame does draw per row is a 1px `--slate-200` bottom border under the TOTAL CYCLE TIME cell only** — 120px wide, exactly that column, on every row including the last. It reads as an underline under the figure, not as a divider. Built as drawn: it is how the frame marks the pivot column in a 24-column table with no other vertical structure. | Yes |
| **R-fc-k** | **Right-alignment starts at TOTAL CYCLE TIME and runs to the end (columns 14–24).** §7.2 says "numeric cells right-aligned", but the frame leaves `W`, `CARDS` and all four dates LEFT-aligned, and it is right to: the dates are read as words and the numeric block reads as one slab against the right edge. `font-variant-numeric: tabular-nums` is **added** — §7.2 asks for tabular figures and the frame sets no numeral feature at all, so this is the spec supplying what the design omitted rather than either overruling the other. | Yes — the aligned set asserted as a contiguous tail, and the numeral feature asserted present exactly once |
| **R-fc-l** | **The Review SLA group is tinted, and the two tiers tint it DIFFERENTLY** — `--status-warning-light` (amber-100) on the group cell, `--slate-50` on the two column cells beneath it, `--amber-700` label text, and the inputs themselves `--amber-50` on `--amber-200`. §7.2 names `--status-warning-light` for the *inputs*; the frame puts that exact value on the *group header* and gives the inputs a lighter fill. Frame wins, and the token §7.2 names is spent where the frame spends it. | Yes — all four surfaces asserted, tokens only |

## Departures taken deliberately

| # | Rule | Asserted |
|---|---|---|
| **R-fc-m** | ⚠️ **THE HEADER IS RAGGED IN THE FRAME AND SOLID IN THE BUILD.** Neither header frame has a background fill; the grey comes from individual cells of different heights (44 / 56 / 60 / 74px), so white gaps show below every cell shorter than its row. That is an artifact of hug-sizing, not a treatment — nothing else in the file does it, and a striped header would read as a defect. Built as one solid band per tier. | Yes — one background owner per tier |
| **R-fc-n** | ⚠️ **THE TIER-ONE BOTTOM RULE IS SHEARED IN `279:22602` AND IS BUILT FULL WIDTH.** Its Header Caption frame is 1648px while its own children sum to 2704px with `clipsContent: false`, so the frame's stroke stops 1056px short of the table's right edge (pixel-verified: the rule runs x=64..1711 and ends). The SAME frame in `279:16649` is 2704px and its rule spans the full width, which settles it as a frame defect rather than an intent. **Frame widths in this file are not authoritative — the cell sums are**; the same latent mismatch sits on the tier-two header and on body row 1, harmlessly, because those carry no stroke. | Yes — the rule asserted on the row, not on a fixed width |
| **R-fc-o** | ⚠️ **NO STICKY HEADER IS CLAIMED AND NO FROZEN COLUMN IS BUILT.** In the 1440 frame both header tiers and all five body rows are siblings offset together by −1392px, so the header scrolls horizontally WITH the body and `MC #` / `DELIVERABLE` scroll clean out of view. Vertical stickiness is simply not determinable from a static frame and nothing in the file indicates it. The build uses the same `.ptable th` sticky recipe the other three tables use — no new mechanism, no invented frozen column — and whether that recipe is inert against page scroll is one of the things only a browser can answer (see the `it.todo` block). | Yes — asserted that the header uses the shared recipe and that no rule pins a column |
| **R-fc-p** | ⚠️ **THE FRAME HAS NO REAL SCROLL CONTAINER; THE BUILD ADDS ONE.** `Request Tab Table` and `Content` are `clipsContent: false` in all three frames, and the 1440 view fakes scrolling by offsetting Content to x=−1392 and letting the top-level frame clip — with the consequence that scrolled-out columns **bleed into the left 64px page gutter** instead of stopping at the table's edge. The build puts the table in the house `.pscrollwrap` / `.pscroll` / `.hslider` trio, which clips at the table's own bounds and never lets the page body scroll sideways. **This forces the one hard wiring change a fourth wide table costs**: `thumbKeyOf` gains an `.fcwrap` branch, app state gains `fcThumb`, and `selectTab` must remeasure on `forecast` or the slider is stale on first mount. | Yes — the wrapper class, the resolver branch and the remeasure list all asserted |
| **R-fc-q** | ⚠️ **NO EMPTY STATE IS DRAWN, IN ANY FRAME.** §8 requires one for every table. Built with the shipped `.rempty` recipe — the same one Requests and Sprint Schedules use — rather than a third variant, with two distinct causes given two distinct states per the rule Requests already states: the search that hid every row, and a board with nothing to forecast. **`.rempty` itself departs from §8 twice** (border `--slate-200` not `--border-border`; 48px vertical padding not 32px) — it is the precedent three tabs already match, so the build matches it and the departure is recorded here rather than split down the middle. | Yes — both states asserted, and the empty state asserted to REPLACE the table |
| **R-fc-r** | **The *How this forecast works* link is drawn in both target frames with nowhere to go.** Its destination — a 480px Helper Panel drawer holding six Formula Cards — is designed only in `279:15122`, which is not a target frame. Built as an in-page anchor to the Model Constants panel, the one destination that exists and the one that answers the question. Raised: the drawer is designed and could be built, and the link changes in one line if product wants it. | Yes — the anchor asserted to resolve to a real id in the same view |

## What was already here and is kept

| # | Rule | Asserted |
|---|---|---|
| **R-fc-s** | ⚠️ **THREE THINGS THE OLD VIEW CARRIED ARE NOT IN §7 AND ARE KEPT — one of them is a 25th column the frame does not draw.** **AC-11 and FR-7.7 require the per-row SAMPLE SIZE to be visible in those words** ("provenance and sample size visible"), so `n` is an acceptance criterion, not decoration; it joins `FC_COLS` as its own trailing `MODEL` group, and the span law derives over 25 exactly as it did over 24. The green model-provenance panel is the other half of the same AC and the only place in the product where BR-3's 2.6–4.6× overstatement is stated to a user. The late-render red treatment on Render Delivery Date is **AC-18**, demoed live on real data; §7.2 does not mention it and §6 protects it in principle ("the alert is dismissible; the fact is not"). The frame independently draws the green banner and a footer banner, so `n` is the only one unattested by the design — and the design is answering §7.2's table, which says nothing about provenance. | Yes — all three asserted present, the green panel keyed on `modelProvenance`, and the AC-11 column asserted by name |
| **R-fc-t** | 🚨 **THE SLA AND CONFIDENCE WRITES HAD NO FAILURE PATH AT ALL, AND NOW DO.** `setSla` sent `Number(ctx.node.value)` unvalidated; the server refuses `<0` or `>60` with a 400, `api.send` throws, and **neither handler had a `try`/`catch`, an optimistic revert, or a banner — and there is no `unhandledrejection` handler anywhere in the app**. The screen therefore kept a number the server had refused, indefinitely, with no signal. Worse, §7.3 requires *"negative and non-numeric rejected without clearing the field"* while a `type="number"` input reports non-numeric text as `''`, which this code read as a deliberate **clear** and used to delete the override. Both now follow the house pattern the four neighbouring writes already use — reject locally by snapping the model back to the last committed value, and optimistic-with-revert plus `flashBanner` for anything the server refuses. | Yes — the guard asserts both handlers contain a revert and a banner, and the reject-not-clear rule is executed |
| **R-fc-u** | **Eleven of the twenty fields `lib/forecast.ts` computes were dropped before reaching the browser**, which is why six of §7.2's columns had no data. The projection in `src/services/pipeline.ts` now carries the whole `Forecast` object. This is a projection widening, not a schema change, not a write, and not a `lib/` edit (invariant 5 untouched). It also **deletes two client-side duplications of verbatim-port arithmetic**: the template computed `sketchReview * 2` for Baseline Review, which is `lib/forecast.ts`'s own `baselineReview` formula retyped in markup, and the lead times would otherwise have been the constant `0.5` hardcoded twice in the browser. | Yes — the wire keys asserted set-equal to the `Forecast` interface's, in both directions, and the retyped arithmetic asserted absent |
| **R-fc-v** | **The render breakdown is byte-identical to the sketch breakdown, today, by construction** — `renderDesign` and `sketchDesign` are both `l`, `renderReview` and `sketchReview` are both `o`, and the two cycles differ only in a lead constant that is `0.5` on both sides. Eight columns where four are duplicates looks like a bug and is not: **§7.1's whole point is parity with the Delivery Forecast sheet's own columns** so the team reads it unchanged. Each block renders its OWN four fields and never copies the other's, so the day the engine distinguishes them the table shows it without an edit. | Yes — the two blocks asserted to read disjoint field sets |
| **R-fc-w** | ⚠️ **STALE SAMPLE VALUES, not data.** The frame's five body rows are not self-consistent: row 1 shows a sketch cycle of 7.39 against lead 0.50 + design 4.80 + review 4.80, which sums to 10.10, and shows different design times in the two breakdown blocks that the engine makes equal. Nothing in the build is calibrated against those numbers. Same class as R-dl-m. | n/a — deliberately not asserted |

## Raised to product (owl)

1. **The Model Constants panel quotes the retired spreadsheet formula** (R-fc-d) — the one item here that would have shipped a number the constitution retired.
2. **`SKETCH` appears twice as a group label; `CYLCE` three times** (R-fc-e, R-fc-f) — shipped as RENDER and CYCLE.
3. **`TYPE` heads the confidence select** and collides with Pipeline's asset-type column (R-fc-g) — shipped as CONFIDENCE.
4. **Difficulty is drawn with a chevron against a spec that says read-only** (R-fc-h) — shipped read-only.
5. **No empty state and no *How this forecast works* destination are drawn** (R-fc-q, R-fc-r).
6. **The tier-one rule is sheared and the header is ragged in the source frame** (R-fc-n, R-fc-m) — built full width and solid.
